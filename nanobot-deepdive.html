第一章

全局鸟瞰：一条消息的完整旅程

在深入每个类之前，先用一张图看看全貌。当你在终端输入一句话，数据会经过哪些"车站"？

你在终端输入: "帮我查一下杭州天气" │ ▼ ┌──────────────────┐ │ CLI 入口 │ commands.py → agent() 函数 │ 加载配置、创建组件 │ Config → Provider → AgentLoop └────────┬─────────┘ │ 通过 MessageBus 发布 InboundMessage ▼ ┌──────────────────┐ │ AgentLoop.run() │ 主循环：不断从总线取消息 │ 取到消息 → _dispatch│ └────────┬─────────┘ │ ▼ ┌──────────────────────────────────────────────────────┐ │ _process_message() ← 这是每条消息的处理入口 │ │ │ │ ① SessionManager.get_or_create() ← 找到/创建会话 │ │ ② ContextBuilder.build_messages() ← 组装提示词 │ │ ├─ 系统提示词 = 身份 + 启动文件 + 记忆 + 技能 │ │ ├─ 历史消息 = 从 Session 取聊天记录 │ │ └─ 用户消息 = 运行时上下文 + 你说的话 │ │ ③ _run_agent_loop() ← 核心循环开始！ │ │ ┌─────────────────────────────────────┐ │ │ │ Provider.chat() → 问 AI 大脑 │ │ │ │ │ │ │ │ │ AI 返回纯文字？→ 循环结束 ✓ │ │ │ │ AI 返回工具调用？ │ │ │ │ │ │ │ │ │ ToolRegistry.execute() → 执行工具 │ │ │ │ │ │ │ │ │ 把工具结果加进对话 → 回到顶部再问 │ │ │ │ （最多循环 40 次） │ │ │ └─────────────────────────────────────┘ │ │ ④ _save_turn() → 保存这轮对话到 Session │ │ ⑤ 打包成 OutboundMessage 发到总线 │ └──────────────────────────────────────────────────────┘ │ ▼ ┌──────────────────┐ │ 终端显示回复 │ "杭州明天晴天 ☀️ ..." └──────────────────┘
一句话总结：CLI 入口负责「启动」，MessageBus 负责「传话」，AgentLoop 负责「想+做」， Provider 负责「问 AI」，Tools 负责「干活」，Session 负责「记录」，Memory 负责「浓缩记忆」。 接下来我们逐个拆开看。
第二章

入口：从 nanobot agent 到 Python 函数

你敲下命令的那一瞬间，发生了什么？

比喻：这就像你按下电视遥控器的开机键——遥控器（终端命令）发出信号， 电视（Python 程序）收到后依次接通电源、调好频道、亮起屏幕。
1

Shell 执行 .venv/bin/nanobot

这是 pip install -e . 时自动生成的脚本。它只做一件事：

from nanobot.cli.commands import app app() # ← 这个 app 是 Typer 应用，它会解析你输入的子命令
2

Typer 路由到 agent() 函数

Typer（一个命令行框架，帮你把 Python 函数变成终端命令）看到你输入的是 agent， 就去执行 commands.py 里被 @app.command() 装饰的 agent() 函数。

3

agent() 函数的 6 步启动

这个函数是整个程序的"总装车间"，它依次做这些事：

① _load_runtime_config() # 读取 ~/.nanobot/config.json → Config 对象 ② sync_workspace_templates() # 确保工作区里的模板文件是最新的 ③ MessageBus() # 创建消息传送带 ④ _make_provider(config) # 根据配置创建 AI 提供商（DeepSeek/OpenAI/…） ⑤ AgentLoop(bus, provider, ...) # 创建大脑指挥部，注册所有工具 ⑥ asyncio.run(run_interactive()) # 启动异步事件循环，进入交互模式
4

交互模式的运行结构

进入交互模式后，程序同时跑着两个"工人"：

工人 A: agent_loop.run() → 不断从总线取消息、处理、发回复 工人 B: _consume_outbound() → 不断从总线取回复、显示在屏幕上 你输入文字 → 包装成 InboundMessage → 丢进总线 → 工人 A 取到 → 处理 → 回复丢进总线 → 工人 B 取到 → 显示在终端
第三章

Config：配置文件怎么变成代码对象

一个 JSON 文件，是怎么变成程序能理解的"指令"的？

比喻：config.json 就像一张点菜单。你写了"要 DeepSeek、8192 tokens"， Pydantic（服务员）拿到菜单后先核对一遍格式对不对，然后把你的要求翻译成厨房能看懂的工单（Config 对象）。
⚙️

Config 类

nanobot/config/schema.py ▶

Config 是整个配置的根。它用 Pydantic（一个数据校验库，能自动检查你填的值对不对）定义了所有配置字段。

字段类型干嘛的
agentsAgentsConfigAI 相关配置（模型名、温度、最大 token 数……）
channelsChannelsConfig聊天渠道配置（Telegram、Discord……）
providersProvidersConfig各家 AI 提供商的 API Key
gatewayGatewayConfig网关配置（端口、心跳间隔）
toolsToolsConfig工具配置（搜索 Key、命令超时、MCP 服务器）

关键方法 — 自动匹配提供商：

_match_provider(model) 的逻辑：

1. 你手动指定了 provider（如 "deepseek"）？→ 直接用它 2. 没指定？看 model 名字： - "deepseek/deepseek-chat" → 前缀 "deepseek" 命中注册表 → 用 DeepSeek - "anthropic/claude-..." → 前缀 "anthropic" → 用 Anthropic 3. 还没匹配上？→ 遍历所有 provider，找第一个填了 API Key 的
📦

AgentDefaults 类

nanobot/config/schema.py ▶
字段默认值含义
model"anthropic/claude-opus-4-5"用哪个 AI 模型
provider"auto"用哪家提供商（auto=自动匹配）
max_tokens8192AI 回复的最大长度（token ≈ 0.75 个中文字）
temperature0.1创造力，0=死板精确，1=天马行空
max_tool_iterations40工具循环最多转几圈（防死循环）
memory_window100攒多少轮对话后触发记忆整理
reasoning_effortnull思考深度（部分模型支持）
第四章

Provider：AI 大脑的"电话线"

Agent 自己不会"想"——它需要打电话给外面的 AI 大脑。Provider 就是这根电话线。

📞

LLMProvider（抽象基类）

nanobot/providers/base.py ▶

这是所有提供商的"合同模板"——不管你是 DeepSeek 还是 OpenAI，都必须实现这些方法：

方法做什么
chat(messages, tools, ...)核心！把对话和工具列表发给 AI，拿回回复。返回 LLMResponse。
get_default_model()返回默认模型名字
_sanitize_empty_content()清理空消息（有些 AI 不接受空内容）

LLMResponse——AI 的回复被包装成这个对象：

字段类型含义
contentstr | NoneAI 说的话（纯文字回复）
tool_callslist[ToolCallRequest]AI 想调用的工具列表
finish_reasonstr"stop"=说完了，"tool_calls"=需要工具
usagedict消耗了多少 token（用于计费）
has_tool_callsbool（属性）有没有工具调用？

ToolCallRequest——AI 想调用工具时，每个请求长这样：

字段含义
id唯一标识（AI 生成的）
name工具名，如 "web_search"
arguments参数，如 {"query": "杭州天气"}
🔌

LiteLLMProvider（最常用的实现）

nanobot/providers/litellm_provider.py ▶

绝大多数提供商都走这个实现。它用 LiteLLM（一个万能翻译器库）来统一不同 AI 的接口。

chat() 方法的内部流程：

① _resolve_model() → 加上提供商前缀（如 "deepseek/deepseek-chat"） ② 构建请求参数 → model, messages, max_tokens, temperature, tools... ③ 设置 API Key → 通过环境变量传给 LiteLLM ④ acompletion() → 异步调用 AI（这是真正发 HTTP 请求的地方！） ⑤ _parse_response() → 把 AI 的原始回复解析成 LLMResponse - 提取 content（文字回复） - 提取 tool_calls（工具调用请求） - 用 json_repair 修复可能畸形的 JSON 参数
第五章

MessageBus：消息传送带

最简单但最重要的组件——它让所有部件不用直接认识对方，通过传送带间接合作。

比喻：就像寿司店的传送带。厨师（渠道/Agent）把食物放上去， 食客（Agent/终端）从传送带上取。厨师不需要知道谁在吃，食客也不用跑进厨房。
🚌

MessageBus

nanobot/bus/queue.py ▶

内部就两条队列（asyncio.Queue），极其简单：

队列方向谁放入谁取出
inbound进站渠道 / CLIAgentLoop
outbound出站AgentLoop渠道管理器 / CLI
方法做什么
publish_inbound(msg)把用户消息放到进站传送带
consume_inbound()从进站传送带取一条消息（等待直到有）
publish_outbound(msg)把回复放到出站传送带
consume_outbound()从出站传送带取一条回复

InboundMessage（进站信封）字段：channel（哪个渠道）、sender_id（谁发的）、chat_id（发到哪个聊天）、content（说了啥）、media（附件）、metadata（额外信息）

OutboundMessage（出站信封）字段：channel、chat_id、content、media、metadata

第六章

Session：聊天记录管理员

Agent 怎么知道"我们刚才聊到哪了"？靠 Session。

比喻：Session 就像一个笔记本。每次对话结束，秘书都把这轮内容记在笔记本上。 下次对话时，先翻一下笔记本："哦上次说到 Python 项目了"。
📒

Session（数据类）

nanobot/session/manager.py ▶
字段含义
key会话标识，格式 "channel:chat_id"，如 "telegram:12345"
messages所有消息列表（只追加，不修改历史）
last_consolidated已经被整理进记忆的消息数量（这个数字之前的不用再看了）

关键方法 get_history()：只返回 last_consolidated 之后的消息（还没被整理成记忆的部分）， 并且会对齐到用户消息开头——确保历史记录不会从 AI 回复的半截开始。

🗄️

SessionManager

nanobot/session/manager.py ▶
方法做什么
get_or_create(key)有就取（先查缓存、再查文件），没有就新建
save(session)写入磁盘，格式是 JSONL（每行一个 JSON）
invalidate(key)清除缓存（下次取会重新从文件加载）

存储格式：每个会话存成 workspace/sessions/{key}.jsonl 文件。第一行是元数据（创建时间等），后面每行一条消息。JSONL 的好处是追加写入很快，不用每次重写整个文件。

第七章

ContextBuilder：提示词组装工厂

发给 AI 的不是你那一句话——而是一个精心拼装的"大文档"。ContextBuilder 就是组装这个文档的工厂。

比喻：你让秘书给新同事交代任务，不能只说"帮我查天气"。你得说： "你是我的助理（身份），你擅长搜索和写代码（技能），之前我们讨论过 X（记忆）， 我上次说了 Y 和 Z（历史），现在请帮我查天气（当前请求）。" ContextBuilder 就是把这些信息按顺序拼起来。
🏭

ContextBuilder

nanobot/agent/context.py ▶

系统提示词的拼装顺序（build_system_prompt()）：

第 1 块 ─ 身份 (_get_identity) "你是 nanobot，一个个人 AI 助手" + 运行环境（macOS/Python 3.12） + 工作区路径 + 使用准则 第 2 块 ─ 启动文件 (_load_bootstrap_files) AGENTS.md → 自定义 Agent 行为规则 SOUL.md → 人格设定 USER.md → 用户偏好 TOOLS.md → 工具使用指南 IDENTITY.md → 额外身份信息 （这些文件都在 workspace 下，你可以随时编辑来改变 Agent 的行为！） 第 3 块 ─ 长期记忆 (memory.get_memory_context) "## Long-term Memory\n用户是 Python 开发者，偏好中文回复……" 第 4 块 ─ 始终加载的技能 (always skills) 一些标记了 always=true 的技能说明 第 5 块 ─ 技能目录 (skills summary) 所有可用技能的 XML 摘要，AI 需要时再深入加载

消息列表的组装（build_messages()）：

返回: [系统提示词, ...聊天历史, 用户消息] 用户消息 = 运行时上下文 + 你说的话 运行时上下文包括：当前时间、时区、渠道名、聊天 ID （这样 AI 知道"现在是几点""你是从 Telegram 来的"） 如果有图片附件： → 读取图片 → Base64 编码 → 拼成多模态消息 → [{type: "image_url", ...}, {type: "text", text: "你说的话"}]
第八章 · 核心

AgentLoop：大脑指挥部

这是整个项目最核心的类。搞懂它，你就搞懂了 nanobot 的 80%。

🧠

AgentLoop — 构造函数

nanobot/agent/loop.py ▶

创建时需要传入的"零件"：

参数是什么
bus消息传送带
providerAI 电话线
workspace工作目录路径
model模型名

🔄

_run_agent_loop() — 核心中的核心

nanobot/agent/loop.py ▶

这个方法实现了经典的 ReAct 循环（Reason + Act）：想→做→看→再想。

输入：initial_messages（系统提示 + 历史 + 用户消息） 输出：(最终回复, 使用的工具列表, 完整消息列表) iteration = 0 while iteration < max_iterations(40): iteration += 1 # ====== 问 AI 大脑 ====== response = provider.chat(messages, tools, model, ...) if response.has_tool_calls: # AI 说："我要用工具！" # 1) 把 AI 的回复（包含工具调用请求）加进消息列表 context.add_assistant_message(messages, content, tool_calls, ...) # 2) 逐个执行工具 for tool_call in response.tool_calls: result = tools.execute(tool_call.name, tool_call.arguments) # 3) 把工具执行结果加进消息列表 context.add_tool_result(messages, tool_call.id, tool_call.name, result) # 4) 带着新信息回到循环顶部，再问 AI continue else: # AI 返回了纯文字 → 循环结束！ final_content = response.content break return (final_content, tools_used, messages)

看到了吗？每次循环只做两件事：问 AI → 执行工具。 AI 不需要工具了就结束。极其简洁——这也是为什么 nanobot 只有 4000 行代码。

📬

_process_message() — 每条消息的处理入口

nanobot/agent/loop.py ▶

这是 _run_agent_loop() 的"上游管理者"——它负责准备工作和善后工作：

① 检查是不是斜杠命令（/new 清空会话，/help 显示帮助） ② 获取会话 → session_manager.get_or_create(key) ③ 检查是否该整理记忆了（未整理消息 ≥ memory_window？） ④ 设置工具上下文（告诉 message 工具"当前在哪个渠道/聊天"） ⑤ 获取聊天历史 → session.get_history() ⑥ 组装消息列表 → context.build_messages(history, user_msg, ...) ⑦ 调用 _run_agent_loop(messages) ← 核心循环 ⑧ 保存这轮对话 → _save_turn(session, messages) ⑨ 打包回复 → OutboundMessage 发到总线
🏃

run() — 主循环

nanobot/agent/loop.py ▶

一个无限循环，不断从总线取消息：

while self._running: msg = bus.consume_inbound(timeout=1s) # 等 1 秒 if msg is None: continue # 没消息？继续等 if msg.content == "/stop": # 停止命令 _handle_stop() else: asyncio.create_task(_dispatch(msg)) # 异步处理，不阻塞主循环
第九章

Tools：Agent 的双手

AI 大脑说"帮我搜一下"，具体怎么搜？靠工具。每个工具就是一个 Python 类。

🔨

Tool（抽象基类）

nanobot/agent/tools/base.py ▶

所有工具都必须继承这个类并实现三个属性和一个方法：

必须实现作用
name (属性)工具名字，如 "web_search"
description (属性)功能描述（AI 靠这个决定什么时候用它）
parameters (属性)参数定义（JSON Schema 格式，告诉 AI 需要传什么参数）
execute(**kwargs)真正干活的方法，返回一个字符串结果

to_schema() 方法会把上面的信息转换成 OpenAI 的 Function Calling 格式—— 这是 AI 大脑通用的"工具说明书"标准。

📋

ToolRegistry（工具注册表）

nanobot/agent/tools/registry.py ▶

一个字典，存着所有已注册的工具。

方法做什么
register(tool)注册一个新工具
get_definitions()返回所有工具的 schema（发给 AI 看）
execute(name, params)① 类型转换 → ② 参数校验 → ③ 执行工具 → ④ 出错时加提示

每个内置工具一览

📖 ReadFileTool

读文件内容。限 128KB，超了自动截断。路径会被限制在工作区内（安全）。

✏️ WriteFileTool

创建/覆盖文件。自动创建父目录。UTF-8 编码。

🔧 EditFileTool

精确查找替换。找不到时用 difflib 给出"你是不是想改这里？"的建议。

📂 ListDirTool

列出文件夹内容。📁 表示目录，📄 表示文件。

💻 ExecTool

执行终端命令。有黑名单过滤（禁止 rm -rf、format 等危险操作）。超时 60 秒自动杀掉。输出截断到 1 万字符。

🌐 WebSearchTool

用 Brave Search API 搜索互联网。返回标题、URL、摘要。

📄 WebFetchTool

抓取网页内容。用 Readability 算法提取正文（过滤广告导航等噪音）。

💬 MessageTool

主动发消息（不是回复）。定时任务完成后就靠它通知你。

🐣 SpawnTool

派出子 Agent 做后台任务。主 Agent 可以继续做别的事。

⏰ CronTool

管理定时任务：创建、列出、删除。支持一次性、间隔重复、cron 表达式。

🔌 MCPToolWrapper

MCP 外部工具的包装器。把外部工具服务器的能力包装成内置工具同样的接口。

第十章

Memory：记忆的浓缩与持久化

聊了几百轮后，会话记录会越来越长。Memory 系统负责把冗长的对话"蒸馏"成精华。

🧠

MemoryStore

nanobot/agent/memory.py ▶

管理两个文件：

文件比喻内容
MEMORY.md身份证/备忘录长期事实："用户是 Python 开发者，偏好中文"——随时被全量覆盖更新
HISTORY.md日记本时间线记录："[2026-03-08 17:00] 讨论了项目架构"——只追加不修改

consolidate() 记忆整理流程：

触发条件：未整理消息数 ≥ memory_window(100)，或用户输入 /new ① 读取当前 MEMORY.md 内容 ② 把未整理的对话格式化成文本： "[17:00] user: 帮我查天气" "[17:01] assistant [tools: web_search]: 杭州明天晴..." ③ 构造一个特殊提示词，告诉 AI： "你是记忆整理助手，请调用 save_memory 工具" ④ 给 AI 一个 save_memory 工具（只有两个参数）： - history_entry: 一段 2-5 句话的摘要，用于追加到 HISTORY.md - memory_update: 更新后的完整长期记忆，用于覆盖 MEMORY.md ⑤ AI 调用 save_memory → 写入文件 ⑥ 更新 session.last_consolidated（标记哪些消息已整理过了）
第十一章

Skills：可热插拔的技能包

技能不是硬编码在程序里的——它们是独立的 Markdown 文件，随时可以增删改。

🎯

SkillsLoader

nanobot/agent/skills.py ▶

技能从哪来？两个来源（工作区优先）：

来源 1 (优先): workspace/skills/{name}/SKILL.md ← 你自己写的 来源 2 (兜底): nanobot/skills/{name}/SKILL.md ← 内置的 同名时工作区版本覆盖内置版本（方便你自定义）

技能怎么被加载进对话？渐进式加载：

① 启动时：build_skills_summary() 生成一份 XML 摘要： <skills> <skill name="weather" description="查天气" available="true"/> <skill name="github" description="操作 GitHub" available="true"/> </skills> ② 这份摘要放进系统提示词 → AI 知道有哪些技能可用 ③ AI 决定"我需要 weather 技能" → 通过技能加载机制 → load_skill("weather") → 读取完整 SKILL.md 内容 → 注入到下一轮的系统提示词中 这样做的好处：不用每次都加载所有技能（太长会浪费 token）， 只在需要时按需加载。

always=true 技能：在 SKILL.md 的 YAML 头部标记 always: true， 该技能会在每次对话时都自动加载，不用等 AI 决定。

第十二章 · 终章

完整流程：源码级逐行追踪

现在把所有零件串起来。你在终端输入"帮我查一下杭州天气"，代码到底怎么跑的？每一步都标注了对应的文件和方法。

①

终端输入 → CLI 入口

commands.py → agent() → run_interactive()

你输入的文字被 prompt_toolkit 读取 → 包装成 InboundMessage(channel="cli", sender_id="user", chat_id="direct", content="帮我查一下杭州天气") → bus.publish_inbound(msg) # 丢进传送带
②

AgentLoop.run() 取到消息

loop.py → run() → _dispatch(msg)

主循环 consume_inbound() 取到了这条消息 → 创建异步任务 _dispatch(msg) → 获取 _processing_lock（同一时间只处理一条消息） → 调用 _process_message(msg)
③

_process_message() 处理

loop.py → _process_message()

→ session = session_manager.get_or_create("cli:direct") # 从文件加载或创建新会话 → 检查未整理消息数 < 100？不用整理记忆，继续 → _set_tool_context("cli", "direct") # 告诉 message 工具和 cron 工具当前在哪个渠道 → history = session.get_history() # 取出上次整理记忆后的所有消息 → messages = context.build_messages( history=history, current_message="帮我查一下杭州天气", channel="cli", chat_id="direct" )
④

ContextBuilder 组装消息

context.py → build_messages() → build_system_prompt()

系统提示词 = [ "你是 nanobot，一个个人 AI 助手...", # 身份 "当前系统: macOS arm64, Python 3.12...", # 环境 "--- AGENTS.md 内容 ---", # 启动文件 "--- SOUL.md 内容 ---", "## Long-term Memory\n用户偏好中文...", # 长期记忆 "<skills>...</skills>", # 技能摘要 ].join("\n\n---\n\n") 用户消息 = "[Runtime Context] time=2026-03-08T17:30+08:00, channel=cli\n\n帮我查一下杭州天气" 最终: [ {role: "system", content: 系统提示词}, ...历史消息..., {role: "user", content: 用户消息} ]
⑤

_run_agent_loop() 第 1 轮

loop.py → _run_agent_loop() → provider.chat()

iteration = 1 → provider.chat(messages, tools=[ {name:"read_file", ...}, {name:"write_file", ...}, {name:"exec", ...}, {name:"web_search", ...}, {name:"web_fetch", ...}, {name:"message", ...}, ... ]) → LiteLLM 发 HTTP 请求到 DeepSeek API → DeepSeek 返回: response.has_tool_calls = true response.tool_calls = [ ToolCallRequest( id="call_abc123", name="web_search", arguments={"query": "杭州 明天 天气"} ) ]
⑥

执行工具：web_search

tools/registry.py → execute() → tools/web.py → WebSearchTool.execute()

→ context.add_assistant_message(messages, tool_calls=...) # 把 AI 的工具调用请求加进消息列表 → tools.execute("web_search", {"query": "杭州 明天 天气"}) → 类型转换: cast_params() → 参数校验: validate_params() → WebSearchTool.execute(query="杭州 明天 天气") → HTTP GET api.search.brave.com/res/v1/web/search?q=杭州+明天+天气 → 返回: "1. 杭州明天晴 25°C..." → context.add_tool_result(messages, "call_abc123", "web_search", "1. 杭州明天晴 25°C...") # 把工具结果加进消息列表
⑦

_run_agent_loop() 第 2 轮

loop.py → provider.chat()（带着工具结果再问一次）

iteration = 2 → provider.chat(messages_with_tool_result, tools=...) → DeepSeek 看到搜索结果，觉得够了 → response.has_tool_calls = false → response.content = "杭州明天是晴天☀️，气温15~25°C，微风，很适合出门！" → 循环结束！return ("杭州明天是晴天...", ["web_search"], messages)
⑧

保存 & 回复

loop.py → _save_turn() → bus.publish_outbound()

→ _save_turn(session, messages) # 把这轮新增的消息追加到 Session # session_manager.save(session) → 写入 sessions/cli:direct.jsonl → OutboundMessage(channel="cli", chat_id="direct", content="杭州明天是晴天☀️...") → bus.publish_outbound(msg) # 丢进出站传送带 → CLI 的 _consume_outbound() 取到回复 → rich.Markdown 渲染后显示在终端 🎉 你看到了回复！
恭喜你走完了全程！从你敲下回车到看到回复，代码经过了： commands.py → MessageBus → AgentLoop.run() → _process_message() → ContextBuilder → _run_agent_loop() → Provider.chat() → ToolRegistry.execute() → Provider.chat()（第 2 轮）→ Session.save() → MessageBus → 终端显示。

每个文件各司其职，互不耦合——这就是为什么 4000 行代码就能做一个完整的 AI Agent。
